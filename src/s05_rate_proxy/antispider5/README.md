# antispider5 · 单 IP 频率限制

案例描述（逐字引自 <https://scrape.center/>，未做任何改写）：

> 限制单个 IP 访问频率 5 分钟最多 10 次，如果过多则会封禁 IP 10 分钟。

## 一、先算账，再动手

页面本身是 SSR 的电影列表（和 ssr1 同一套 Vue + Element UI 模板），没有任何
JS 加密、没有验证码、没有 UA 检测——**唯一的对抗点就是「你一共发了几次请求」**。

配额是 10 次 / 300 秒，所以耗时只由请求数决定：

| 抓法 | 请求数 | 理论下界 | 35s 间隔预算 | 结论 |
|---|---:|---:|---:|---|
| 11 个列表页 | 11 | 5.5 min | 5.8 min | ✅ 跑 |
| 列表 + 全部 100 个详情页 | 111 | 55.5 min | 64.7 min | ❌ 太久，只跑样本 |

这张表决定了本案例的抓取范围：**列表页跑全量，详情页只跑样本。**
（`spider.py --plan` 可以只打印预算不发请求。）

## 二、控速参数

```
最小间隔     35 秒     （300/10 = 30 秒是刚好打满；取 35 秒留余量）
窗口容量     9 次/300s （站点声明 10 次，留 1 次余量）
并发         1（串行）
```

35 秒的推导：任一 300 秒窗口里最多落进 `floor(300/35) + 1 = 9` 次请求，
所以**即便服务端用的是固定 5 分钟桶而不是滑动窗口，也不会超过 10 次**。
详见 `../README.md` 第二节。

**这是主动控速，不是撞墙重试**：`RateLimiter.acquire()` 在请求发出**之前**就先
睡够，退避重试（`PoliteClient._backoff`）只是兜底。本案例实跑中退避路径一次
都没被触发。

## 三、实测结果

```
$ .venv/bin/python src/s05_rate_proxy/antispider5/spider.py --details 6 --gap-probe 4

站点声明总数：104
page 1..10: 每页 +10 → 100/104
page 11:    +0 → 100/104          ← 翻页到此为止
gap probe /detail/101..104 → 500  ← 缺口探针，见第四节
detail 1..6                        ← 详情页样本

完成：翻页全量 100 条（站点声明 104 条），详情样本 6 条，缺口探针 4 条；
      用时 11.9 分钟，限流命中 0 次
```

| 指标 | 值 |
|---|---|
| 抓取范围 | 列表页**翻页全量** 100 条 + 详情页**样本** 6 条 + 缺口探针 4 次 |
| 请求数 | 21（11 列表 + 4 缺口探针 + 6 详情） |
| 最小间隔 / 窗口容量 | 35 秒 / 9 次每 300 秒 |
| 耗时 | **11.9 分钟**（其中纯等待 681.7 秒） |
| 下行字节 | 1 919 491 |
| 限流命中（429/403/拦截页） | **0** |
| 退避重试 | 0 |
| 被封禁 | **否**（全程未触发） |

**哪些是全量、哪些是样本，说清楚：**

- ✅ **列表数据是全量**：翻到 `/page/11` 返回 0 条，分页已穷尽，100 条一条不少。
- ⚠️ **详情页只跑了 6 条样本**。抓满 100 个详情页需要 100 次请求，
  按 35 秒间隔约 **57.8 分钟**（这个数字由 `run.detail_full_would_cost` 实算写入
  JSON）。样本用来验证详情页解析链路（`drama` 剧情简介等列表页没有的字段）跑得通，
  **不能当成全量详情**。
- ✅ **缺口探针 4 次**：见下节。

## 四、100 条 vs 站点声明的 104 条

分页控件渲染的是 `共 104 条`，但翻页只能翻出 100 条。这个差额不能含糊过去，
所以 `spider.py --gap-probe` 按 id 直接探了缺的那 4 条：

```
GET /detail/101 → HTTP 500
GET /detail/102 → HTTP 500
GET /detail/103 → HTTP 500
GET /detail/104 → HTTP 500
```

四条全是 **500**，不是 404。也就是说：这 4 条记录在计数查询里存在（所以
`共 104 条` 里算了它们），但详情视图渲染时报错——多半是数据本身残缺
（缺封面/缺关联字段之类）导致模板取值失败。列表接口把它们过滤掉了，详情页
挡不住就 500。

结论：**100 条就是这个站通过公开页面能拿到的全部数据**，缺的 4 条不是我们漏抓，
而是站点侧取不出来。原始状态码记在 `data/antispider5_movies.json` 的
`gap_probe.results` 里。

> 同样的 100 vs 104 在 antispider6 上也复现了（那是同一份电影数据的另一个部署），
> 佐证这是数据侧的问题而不是抓取侧的。

## 五、字段与落盘

`data/antispider5_movies.json`（57 KB，未触发降级）：

```json
{
  "id": 1,
  "name": "霸王别姬",
  "name_en": "Farewell My Concubine",
  "categories": ["剧情", "爱情"],
  "regions": ["中国内地", "中国香港"],
  "duration": "171 分钟",
  "published_at": "1993-07-26",
  "score": 9.5,
  "cover": "https://p0.meituan.net/movie/ce4da3e03e655b5b88ed31b5cd7896cf62472.jpg@464w_644h_1e_1c",
  "detail_url": "/detail/1"
}
```

同一份 JSON 里还有：

- `request_timeline`：**每一次请求**的时刻、URL、状态码、发前等待秒数、耗时、字节数。
  这是「全程没被封」的可核查证据——21 条记录全是 200。
- `summary`：100 条的统计摘要（评分 min 8.8 / max 9.5 / mean 8.97 / median 8.9；
  类别 22 种，剧情 68、爱情 28、奇幻 25……；地区 23 种，美国 51、中国香港 14、英国 14……）。
- `gap_probe`：第四节那 4 次探针的原始状态码。
- `detail_samples`：6 条详情样本（含 `drama` 剧情简介）。
