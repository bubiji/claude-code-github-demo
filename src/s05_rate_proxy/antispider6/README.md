# antispider6 · 单账号频率限制

案例描述（逐字引自 <https://scrape.center/>，未做任何改写）：

> 限制单个账号访问频率 5 分钟最多 10 次，如果过多则会暂停访问 10 分钟。

## 一、和 antispider5 的唯一区别：配额挂在哪

数据、模板、分页协议都跟 antispider5 一模一样（同一份 104 条电影数据的另一个部署）。
差别只有一处——**配额跟着账号走，不跟着 IP 走**。这一处差别改变了全部策略：

| 手段 | antispider5（限 IP） | antispider6（限账号） |
|---|---|---|
| 代理池换出口 IP | 有用 | **完全无效**——配额跟着 `sessionid` |
| 注册新账号 | 无意义（不需要登录） | 有用 |
| 主动控速 | 有用 | 有用 |

**识别「配额挂在哪个维度上」，比手里有多少代理重要得多。** 这个站上，代理池这个
工具从一开始就是错的答案。

## 二、登录

首页 `/` 直接就是登录页（`login.css`），POST 到 `/login`：

```
GET  /login                                    → 200，表单只有 username / password
                                                 （实测**没有** csrfmiddlewaretoken）
POST /login  username=admin&password=admin     → 302 Location: /
                                                 Set-Cookie: sessionid=...
```

练习站公开凭据 `admin` / `admin`，已核实可用。

**省一次请求的小动作**：登录用 `allow_redirects=False`。`sessionid` 在 302 的
`Set-Cookie` 里就已经下发了，让 requests 自动跟随 302 会白白多花一次配额去取
首页——而首页的内容跟 `/page/1` 完全一样，后面本来就要抓。12 次请求里省 1 次
就是省 8%。

> `sessionid` 是真实凭据，本仓库是公开仓库，落盘时经 `common.redact()` 脱敏为
> `oxn2yj…adpvsr（已脱敏，原长 32）`。公开的 `admin/admin` 可以写进代码，
> 换来的 sessionid 不行。

## 四、受控限流探测：`probe.py`

「全程没被封」有个尴尬：它跟「这个站根本没有限流」在观测上长得一模一样。
要看到一次真实的拦截，通常得付出自己被封 10 分钟的代价。

**这个站给了一条不用自己挨封的路：配额挂在账号上，而 `/register` 开放注册。**
于是 `probe.py` 的设计是——**先决定谁来承担代价，再去触发它**：

- 探测全程使用一个**一次性注册的账号**（`probe_<8 位随机>`），正式抓取用的
  `admin` 账号完全不参与；
- 探测在全量抓取**跑完之后**执行，不占正式配额；
- 两道安全闸：`--max` 次数上限（默认 14），以及**第一个非 200 立刻停手**
  ——不在封禁期里反复撞（撞了会续期）；
- 一次性账号如果注册/登录失败，脚本**直接放弃并退出**，绝不回退到 `admin`
  （代码里就是这么写的：「不改用 admin 账号——那会牺牲正式身份」）。

（更早一轮 `--no-recovery`（账号 `probe_2qfxfwvj`）测到的是 49.2 秒内 11 次成功、
第 12 次 403，与本轮一致。）

**测到的事实**（12 条请求的原始时间线在 `data/rate_limit_probe.json` 的 `items`；
恢复阶段的逐次探针见下面的控制台记录）：

- 在 48.8 秒内，同一账号连发 **11 次成功**，**第 12 次返回 HTTP 403**（响应体只有 22 字节）；
- 拦截以 **403** 呈现，**不带 `Retry-After` 响应头**——所以客户端拿不到官方的等待时长，
  退避只能按站点文案里的 10 分钟兜底（`common.BAN_SECONDS = 600`）；
- 加上登录那 1 次请求，该账号在被拦之前一共完成了 12 次请求。站点文案写的是
  「5 分钟最多 10 次」，实测放行到 11 次页面请求才拦——**实现比文案略宽松**。
  这正好说明为什么我们的控速参数取 9 次 / 300 秒而不是踩着 10 去卡：
  阈值的确切语义（算不算登录、`>` 还是 `>=`）是猜不准的，留余量比猜便宜。

### 实测：恢复

拦下之后每 30 秒探一次，直到恢复（同一个一次性账号）：

```
[20:01:51] #12 t+ 48.8s  HTTP 403  22B          ← 拦截
[20:01:51] 开始恢复计时，每 30s 探一次，最长 15 分钟
[20:02:21]   恢复探针 t+30s  → HTTP 403
[20:02:51]   恢复探针 t+60s  → HTTP 403
   …（中间 17 次全部 403，逐条记录在 data/rate_limit_probe.json）…
[20:11:22]   恢复探针 t+571s → HTTP 403
[20:11:54]   恢复探针 t+603s → HTTP 200 ok
[20:11:54] 恢复用时：602.7s
```

**恢复用时 602.7 秒 = 10.0 分钟**，与案例文案写的「暂停访问 10 分钟」严丝合缝。

顺带测到一件事：**恢复期内的 20 次探测请求没有让封禁续期**——封禁是从触发时刻起算
的固定 10 分钟窗口，不因期间继续请求而延长（至少这个实现是这样）。
但代码里仍然不敢依赖这一点：`PoliteClient` 一旦识别出限流，退避下限就是
`BAN_SECONDS = 600`，绝不在封禁期里高频重试——换个实现（比如「最后一次违规起算」）
就会被自己拖成无限封禁。

### 三个数字对上了

| | 站点文案 | 实测 |
|---|---|---|
| 阈值 | 5 分钟最多 10 次 | 48.8 秒内 11 次成功，第 12 次 403（实现略宽松） |
| 惩罚 | 暂停访问 10 分钟 | **602.7 秒 = 10.0 分钟** |
| 惩罚对象 | 单个账号 | 一次性账号被拦期间，`admin` 账号的抓取不受影响 |

这也反过来印证了控速参数的余量是对的：我们跑的是 9 次 / 300 秒、间隔 35 秒，
离 48.8 秒 11 次这条实测红线差着一个数量级。

### 一个副产品：`/register` 会 502

同一段代码连跑两次，第二次 `POST /register` 返回了 nginx 的
**502 Bad Gateway**（响应体是 nginx 默认错误页），第三次又恢复正常。
成功那次的 `POST /register` 耗时约 8 秒——注册接口本身很慢，nginx 上游超时
偶发。脚本对此的处理是**如实记录状态码并退出**，不重试、不改用 `admin`。
