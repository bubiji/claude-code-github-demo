# 阶段 5：频率限制与代理池（antispider5 / antispider6 / antispider7 / tool1）

前四个阶段的反爬是**判定题**——服务端看一眼你的请求，觉得像爬虫就拒绝，改头换面
就能过。这个阶段不一样：**服务端不判断你是谁，只数你发了几次。**

```
限制单个 IP   访问频率 5 分钟最多 10 次   →  antispider5
限制单个账号  访问频率 5 分钟最多 10 次   →  antispider6
IP 与账号     双重限制                    →  antispider7
公开代理池 API                            →  tool1
```

数数是没法伪装的。于是本阶段的全部功夫都花在两件事上：**把发送速率压到阈值以下**，
以及**在同样的配额下少发几次请求**。

```
src/s05_rate_proxy/
├── common.py           # 三层共用逻辑：控速 / 传输 / 代理池
├── antispider5/        # IP 限流   —— 全量 104 部电影 + 详情页样本
├── antispider6/        # 账号限流 —— 全量 104 部电影；probe.py 用一次性账号实测阈值
├── antispider7/        # 双重限流 —— 全量 9040 本书；靠加大 limit 把请求数降到 1/100
└── tool1/              # 代理池   —— 取 → 校验 → 剔除，量出真实可用率
```

## 一、先算账：预算表

这一步必须在写抓取代码**之前**做完。配额是 10 次 / 300 秒，所以一次抓取要多久，
**只取决于你打算发多少个请求**，跟带宽、并发、机器快慢全都没关系：

```
理论下界 = 请求数 / 10 * 300 秒      （把配额刚好用满）
实际耗时 = (请求数 - 1) * 35 秒      （我们留了安全余量的固定间隔，见第二节）
```

| 案例 | 抓法 | 请求数 | 理论下界 | 35s 间隔预算 |
|---|---|---:|---:|---:|
| antispider5 | 11 个列表页（104 部电影） | 11 | 5.5 min | **5.8 min** |
| antispider5 | 列表 + 全部 104 个详情页 | 115 | 57.5 min | 66.5 min ❌ |
| antispider6 | 登录 + 11 个列表页 | 12 | 6.0 min | **6.4 min** |
| antispider7 | 登录 + 前端 limit=18 翻 503 页 | 504 | 252 min | 293 min ❌ |
| antispider7 | 登录 + limit=2000 翻 5 页 | 6 | 3.0 min | **2.9 min** |

**这张表就是本阶段的全部设计依据。** 打 ❌ 的两行不是「慢一点」，是「做不完」——
看到 66 分钟和 293 分钟这两个数字，才会去想「能不能少发几次请求」，而不是
「能不能发快一点」。答案见第三节。

## 二、控速：为什么是 35 秒、9 次

`common.py` 的 `RateLimiter` 同时挂了两道闸，取满足条件的**较晚**时刻放行：

| 参数 | 站点声明 | 我们取值 | 为什么 |
|---|---|---|---|
| 窗口容量 | 10 次 / 300s | **9 次 / 300s** | 「最多 10 次」的边界值是 `>` 还是 `>=` 不确定；本地时钟与服务端不同步。留 1 次余量代价是慢 10%，收益是不用赌 |
| 最小间隔 | —（未声明） | **35 秒** | 300/10 = 30 秒是「刚好打满」。取 35 秒后，任一 300 秒窗口里最多落进 `floor(300/35)+1 = 9` 次——**即使服务端用的是固定 5 分钟桶而不是滑动窗口，也超不了** |

两道闸缺一不可：

- **只有滑动窗口不够**：窗口允许「瞬间连发 9 次再干等 300 秒」。如果服务端是固定桶
  （`django-ratelimit` 的默认实现），这种突发跨过桶边界时，同一个桶里可能落进 10 次以上。
- **只有最小间隔不够**：间隔只约束相邻两次。一旦有重试插队，或多个客户端共用出口 IP，
  窗口内总数照样会超。

### 主动控速 ≠ 撞墙重试

`RateLimiter.acquire()` 是**前置**的：请求发出**之前**先等够，而不是发出去挨了 429
再退避。`PoliteClient` 里的指数退避（full jitter）只是兜底——它一旦被触发，说明我们
对配额的估计错了。所以退避的下限被设成 `BAN_SECONDS = 600`：站点说封 10 分钟，退避
就不能短于 10 分钟，否则就是在封禁期里反复撞墙，把封禁续期。

本阶段三个站的实跑记录：**退避路径一次都没被触发**（`rate_limited_hits: 0`）。

## 三、比控速更有效的一招：让每个请求带回更多数据

配额数的是**请求次数**，不是字节数。所以在被限流的站上，**降低请求条数**的收益
远大于提高速度：

```
antispider7 前端：GET /api/book/?limit=18&offset=N     → 9040 条要 503 个请求
实测该接口没有设置 DRF 的 max_limit
改成          ：GET /api/book/?limit=2000&offset=N    → 9040 条只要 5 个请求
```

同一份全量数据，请求数降到 1/100，耗时从 4.9 小时降到 3.1 分钟，全程零限流。
这不是钻空子，而是这个阶段真正该学到的东西：**先问「这些数据最少几个请求能拿完」，
再去调速度。**

antispider6 上的同类动作是省掉一次重定向：登录用 `allow_redirects=False`，
只花 1 次请求拿 `sessionid`，不让 requests 自动跟随 302 白花一次配额。

## 四、代理池只是补充手段

`tool1` 的实测漏斗（完整数据见 `tool1/README.md`）：240 次 API 调用只换来 **26** 个
去重候选（池子本身就这么大），其中能走明文 HTTP 的 11 个（42.3%），能走 HTTPS 的
3 个（11.5%），**真能把 antispider5 页面取回来的只有 2 个（7.7%）**——而
antispider5/6/7 全是 HTTPS 站。

把「换 IP」当主要手段，等于把成功率押在这个数字上。所以本阶段的正确顺序是：

1. **先控速**——这一步就足以让全程零封禁（三个站实跑均为 0 次限流命中）；
2. **再减请求数**——把 503 个请求变成 5 个；
3. **代理垫底**——只在意外挨封时用来避免干等 10 分钟，以及用来做那些「会把 IP 打封」
   的实验（见下节）。

另外，`antispider6` 限的是**账号**不是 IP，代理池对它**完全无效**——配额跟着
`sessionid` 走，换出口 IP 不改变任何事。识别「配额挂在哪个维度上」，比手里有多少
代理重要得多。

## 五、怎么在不封自己的前提下证明限流是真的

「全程没被封」这件事有个尴尬：它跟「这个站根本没有限流」在观测上长得一模一样。
要区分两者就得看到一次真实的拦截，而看到拦截的代价通常是自己被封 10 分钟。

`antispider6/probe.py` 的解法是**换一个身份来承担代价**：

- antispider6 的配额挂在**账号**上，而该站 `/register` 开放注册；
- 探测全程使用一个**一次性注册的账号**，正式抓取用的 `admin` 账号不参与；
- 探测在全量抓取**跑完之后**才执行，不占正式配额；
- 两道安全闸：`--max` 次数上限（默认 14），以及**拿到第一个非 200 立刻停手**
  ——不在封禁期里反复撞（撞了会续期）。

实测（账号 `probe_fp8zbzni`，完整过程见 `antispider6/README.md` 第四节）：

| | 站点文案 | 实测 |
|---|---|---|
| 阈值 | 5 分钟最多 10 次 | 48.8 秒内 **11 次成功，第 12 次 HTTP 403**（无 `Retry-After`） |
| 惩罚 | 暂停访问 10 分钟 | **602.7 秒 = 10.0 分钟** |
| 惩罚对象 | 单个账号 | 一次性账号被拦期间，`admin` 账号的抓取不受影响 |

**受控的含义是：先设计好谁来承担代价，再去触发它**，而不是先撞了再说。
这组数字同时印证了控速参数的余量——我们跑的是 9 次 / 300 秒、间隔 35 秒，
离「48.8 秒 11 次」这条实测红线差着一个数量级。

antispider5（IP 限流）没有等价的「一次性身份」，所以对它不做主动越界探测。
tool1 那 2 个可用代理理论上可以代打，但那是拿别人的 IP 换我的实验数据、
且 2 个样本的结论也不可靠，所以没做。IP 侧的证据来自它自己的案例描述、
antispider6 上量到的同族阈值，以及本阶段完整的请求时间线（每个 JSON 的
`request_timeline` 字段，逐条记录状态码与等待时长）。

## 七、练习伦理

scrape.center 是案例作者公开提供的**专用练习平台**。本阶段全部代码串行发送、
间隔 ≥35 秒、并发写死为 1，配额只用到声明值的 90%，不做任何压测；
`probe.py` 的越界探测限定在一次性账号上，且总请求数不超过 14 次。
