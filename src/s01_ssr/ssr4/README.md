# ssr4 —— 每响应 5 秒延迟：并发与超时

案例描述（**逐字引自** https://scrape.center/，未改写）：

> 电影数据网站，无反爬，每个响应增加了 5 秒延迟，适合测试慢速网站爬取或做爬取速度测试，减少网速干扰。

这 5 秒是服务端**故意注入的等待**，不是带宽瓶颈——瓶颈在「等」不在「算」，所以线程池
就够，不必上 asyncio。但「开并发」和「真的变快」是两件事：能不能快，取决于**服务端
愿意同时处理几个请求**。所以本案例先实测再决定开几路，而不是拍脑袋写个 `workers=16`。

## 怎么跑

```bash
cd src/s01_ssr/ssr4
python crawl.py --bench            # 只测并发梯度（HTTP/1.1 多连接），不抓数据
python crawl.py --bench --h2       # 追加 HTTP/2 单连接多路复用对照
python crawl.py                    # 默认 4 路并发、60s 超时，抓全量（约 5.5 分钟）
python crawl.py --no-detail        # 只抓 10 个列表页，约 37 秒
python crawl.py --timeout 3        # 复现「超时小于 5s 注入延迟」的翻车
```

## 一、先测清楚：并发到底有没有用

`--bench` 让 N 路同时打 N 个不同的详情页，看墙钟时间是不是随 N 摊薄。
判据很简单：服务端**并行**处理的话 `wall ≈ 6s` 恒定；**串行**的话 `wall ≈ N × 6s`，并发白开。

### 第一轮（2026-08-23 19:25–19:28，`data/bench-round1.json`）

| 并发 N | HTTP/1.1 墙钟 | 折合 | HTTP/2 单连接墙钟 | 折合 |
|---|---|---|---|---|
| 1 | 6.51s | 6.51s/请求 | 6.44s | 6.44s/请求 |
| 2 | 11.92s | 5.96s/请求 | 11.88s | 5.94s/请求 |
| 4 | 23.85s | 5.96s/请求 | 23.71s | 5.93s/请求 |
| 8 | 46.99s | 5.87s/请求 | 26.43s | 3.30s/请求 |

HTTP/1.1 这一列是教科书式的**单队列串行**：8 路的单请求耗时是
`5.87 / 11.64 / 17.67 / 23.20 / 29.52 / 35.05 / 40.32 / 46.98`——等差数列，公差就是那 5 秒多。
按这一轮的读数，结论是「并发完全无效」。

### 第二轮（2026-08-23 19:37–19:40，`data/bench.json`，同一台机器、同一条网络）

| 并发 N | HTTP/1.1 墙钟 | 折合 | HTTP/2 单连接墙钟 | 折合 |
|---|---|---|---|---|
| 1 | 6.59s | 6.59s/请求 | 6.37s | 6.37s/请求 |
| 2 | 6.70s | **3.35s/请求** | 6.58s | **3.29s/请求** |
| 4 | 12.78s | 3.19s/请求 | 12.34s | 3.08s/请求 |
| 8 | 23.81s | 2.98s/请求 | 24.62s | 3.08s/请求 |
| 4（重复档） | 13.12s | 3.28s/请求 | 12.06s | 3.01s/请求 |
| 8（重复档） | 25.48s | 3.19s/请求 | 25.47s | 3.18s/请求 |

**同一段代码，隔 12 分钟跑，结论反过来了。** 第二轮里 2 路就把折合耗时砍到一半
（3.35s/请求），而 4 路、8 路再也压不下去，稳定停在 **3.0~3.3s/请求**——重复档位复现良好。

两轮合起来能读出的事实（只说实测能支持的）：

1. **并发上限在服务端，不在客户端。** 客户端从 1 路加到 8 路，吞吐在 2 路时就到顶了；
   继续加线程只是让队尾等更久，一点收益也没有。第二轮的天花板对应「服务端同时处理 2 个请求」。
2. **HTTP/2 单连接多路复用没有额外好处。** 特意做这组对照是为了排除「客户端连接不够」
   这个嫌疑：如果瓶颈在连接层，8 个 stream 走一条 TCP 连接应该明显快于 8 条 HTTP/1.1 连接。
   第二轮两者几乎逐格重合（3.08 vs 2.98），说明瓶颈确实在服务端排队，不在连接数。
   （第一轮 h2 的 8 路 26.43s 快于 h1 的 46.99s，是那一轮里唯一的例外读数，没能在第二轮复现，
   如实留在表里不做解释。）
3. **这个上限会变。** 它是公开练习站，同时可能有别人在打；两轮之间从「1 个」变成「2 个」，
   不是我们改了什么。所以脚本里**不写死并发数**，README 也不给「最佳 workers」这种结论——
   要点是**先量再决定**，量出来的数字连同 `written_at` 一起存进 `data/bench*.json`。

## 二、超时怎么给（这里最容易翻车）

单请求耗时不是 5s，而是：

```
单请求耗时 ≈ 5s（服务端注入延迟） + 排队等待（前面还有几个没被处理完）
```

并发 N 路而服务端一次只处理 k 个时，队尾那个请求要等 `⌈N/k⌉ × 6s`。实测里
`workers=4` 跑全量时，最慢的一个请求花了 **17.6s**——比 5s 大了 3 倍多。
所以超时必须按**队列深度**给，不能按「注入延迟」给。脚本据此做两件事：

- 启动时校验：`timeout ≤ 5` 直接警告「几乎必然超时」；`timeout < workers × 6` 警告偏紧。
- 列表页超时**不当成「翻到头了」**——那会静默少抓一半数据还报成功。捕获后打错误并非 0 退出。

`--timeout 3` 的真实翻车现场（2026-08-23 19:28:50，退出码 2）：

```
[ssr4] 警告：timeout=3.0s 不大于服务端注入的 5s 延迟，请求几乎必然超时。
[ssr4] 串行基线第 1 个请求超时（timeout=3.0s），跳过基线测量。
[ssr4] https://ssr4.scrape.center · workers=1 timeout=3.0s delay=0.0s detail=on
[ssr4] 列表页请求超时（timeout=3.0s）：HTTPSConnectionPool(host='ssr4.scrape.center', port=443):
       Read timed out. (read timeout=3.0)
[ssr4] 这站每个响应固定慢 5s，超时必须显著大于 5s；并发 N 路时还要再算上排队。
```

## 三、串行预计 vs 实际并发耗时（2026-08-23 19:40 全量实跑）

```
[ssr4] 串行基线：3 个请求，单个 5.86~6.90s，均值 6.24s
[ssr4] https://ssr4.scrape.center · workers=4 timeout=120.0s delay=0.0s detail=on
  page 1..10: 各 10 条； page 11: 0 条 → 翻页结束

[ssr4] 抓取完成
  记录数     : 100（列表页 10 页 / 详情页 100 个）
  请求数     : 112，失败 0
  单请求均值 : 10.97s
  总耗时     : 332.93s（列表 46.26s + 详情 286.68s）
  落盘       : ssr4.json 482.8KB / ssr4.summary.json
  并发效果   : 串行预计 699s（112 请求 × 无排队 6.24s） → 实际 333s，加速 2.10×（workers=4，折合 2.97s/请求）
```

| | 串行 | 并发 workers=4 |
|---|---|---|
| 请求数 | 112 | 112 |
| 单请求 | 6.24s（无排队实测均值） | 2.97s（折合） |
| **总耗时** | **699s ≈ 11 分 39 秒（预计）** | **332.93s ≈ 5 分 33 秒（实测）** |
| 加速 | 1× | **2.10×** |

同一轮的 `--no-detail`（只抓 10 个列表页 + 1 次翻页探测，共 12 请求）：
串行预计 73.7s → 实际 **37.2s**，加速 1.98×。两个规模上的加速比一致（≈2×），
和第二轮梯度实测的「服务端同时处理 2 个」互相印证。

### 「串行预计」是怎么算的（这个数最容易被灌水）

- **不用**并发过程中的单请求均值：那个数含排队等待（本轮 10.97s），拿它乘 112 会得到
  1229s 的「串行预计」，加速比就被吹成 3.7×。
- **用**抓取前单独串行打的 3 个请求的均值（`serial_baseline()`，本轮 6.24s，无人排队）：
  `699s = 112 × 6.24s`。这才是「同样的活儿一个个干要多久」。
- 也**不用**并发里最快的那个（本轮 1.10s）当基准——偶发快响应会把基准压得过低。

计算口径连同 `serial_per_request_source` 一起写进了 `data/ssr4.summary.json`，
不是只在 README 里说一句。

## 四、总耗时怎么压到可接受范围

按上面实测的事实排优先级：

1. **先把请求数降下来**——这是唯一由客户端说了算的变量。全量 112 请求（10 列表页 + 1 探测 +
   100 详情页 + 1 页并发批次多打的）5 分 33 秒；只要列表页字段的话 `--no-detail` 是
   12 请求、**37 秒**，拿到 14 个字段里的 10 个（缺 `drama` / `directors` / `actors`，
   以及详情页才有的完整信息）。
2. **并发开到服务端上限就停**：实测上限 2，开到 4 已经只是给队列排队。本案例默认
   `workers=4`（留一点余量，遇到上限变宽时自动吃到），不做「开 16 路」这种压测式操作。
3. **超时按队列深度给**：默认 60s，全量跑用 120s；最慢的一个请求实测 17.6s。
4. **不重复抓**：数据已落盘 `data/ssr4.json`，复跑前先想清楚要不要重抓——这站每跑一次
   全量就是 5 分半的服务端等待，礼貌不只是加 `delay`。

> 「可接受范围」的诚实说法：**在服务端只肯并行 2 个请求的前提下，112 个请求的下限就是
> 约 5.5 分钟**（`112 ÷ 2 × 6s ≈ 336s`，实测 332.93s——已经贴着下限了）。再想快只能少发请求，
> 客户端这边没有别的余地。任何声称能在这站把全量压到 1 分钟的方案，不是在压测就是在编。

## 遇到的坑

1. **`requests.Session` 不保证线程安全。** 4 路共用一个 Session 会在并发下出怪问题
   （连接池竞争、偶发的连接复用错乱）。改成 `threading.local()` 每线程一个 Session，
   并把 `HTTPAdapter(pool_connections=workers, pool_maxsize=workers)` 配足——
   默认池大小是 10，工作线程多于它时 urllib3 会打 `Connection pool is full` 并丢弃连接。

2. **拿并发均值当串行基准 = 自吹加速比。** 见上面「串行预计是怎么算的」。这个坑很隐蔽，
   因为算出来的数字「看起来很合理」，而且没人会去质疑一个 3.7×。

3. **并发下的翻页会多打一页。** `crawl()` 按批并发翻页：`workers=4` 时一次探 4 页，
   第 3 批探的是 9/10/11/12 页，虽然 11 页已经 500（没有下一页）了，12 页那一发还是打出去了。
   所以全量请求数是 **112** 而不是串行的 111。知道这一发从哪来，比强行让它等于 111 重要。

4. **列表页超时被当成「翻到头了」是最坏的失败模式。** `crawl()` 靠「解析不出条目」终止翻页，
   而超时抛出的异常如果被吞掉、返回 `""`，就正好长得像「没有下一页」——脚本会少抓一半数据、
   报成功、退出码 0，没有任何人会发现。所以 `requests.exceptions.Timeout` 单独捕获、
   打明原因、退出码 2。

5. **别把 5 秒当成「本站唯一的耗时」。** 实测最快的一个请求 1.10s（比注入延迟还短），
   最慢 17.6s（排队）。真实分布远比「固定 5s」宽，超时和进度预估都得按分布给，不能按标称值给。
